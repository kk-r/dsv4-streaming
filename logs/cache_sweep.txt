NOTES
1. Throughput falls as the cache grows. Hit rate rises monotonically with
   cache size (0.434 @4G -> 0.669 @32G) but tok/s moves the other way past
   8 GB: the extra hits do not pay for the memory pressure they create.
2. Hits/misses/read_gb are deterministic per cache size - every run of a
   given size did byte-identical work and produced identical output text.
   Only wall time varies, so all timing differences are system effects.
3. pass1-fwd is contaminated: swap grew 1520 -> 6657 MB during it, driven by
   the 24 GB and 32 GB runs. Swap never recovered afterwards (stayed ~7 GB
   for the rest of the sweep). Small-cache runs did not grow swap.
4. One transient collapse observed: pass3-fwd @8 GB took 726.4 s for work
   that takes ~11.7 s (62x), at only 17.7 GB peak memory. Three immediate
   replicates at 8 GB returned 2.04/2.03/2.08 tok/s, so the collapse is a
   sporadic system-level I/O stall, NOT a property of any cache size.
5. 4 GB and 8 GB are within noise of each other (2.00 vs 2.04 median, best
   2.01 vs 2.08): the optimum is a plateau at 4-8 GB, not a sharp peak.
   The clear signal is the decline from 16 GB upward.
6. Baselines for context: llama.cpp CPU-only 1.56-2.0 tok/s; the earlier
   40 GB-cache diverse-prompt run managed 0.05 tok/s on the same prompt.
