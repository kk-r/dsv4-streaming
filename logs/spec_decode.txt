# Speculative decoding via prompt-lookup drafting — engineering + measurement log
# Started 2026-08-15. Hypothesis: decode cost is dominated by per-forward-pass
# overhead (~128 ms model compute + ~300 ms of 43 per-layer Python sync
# round-trips), not per-token weight reads. Verifying k drafted tokens in ONE
# batched forward should amortize the per-pass cost across accepted tokens.
#
# Design decisions (from code reading, before any run):
# - Attention.__call__ has NO batched decode-append: s>1 goes to the prefill
#   branch, which assigns positions 0..s-1 and reseeds the cache via
#   _seed_cache. So spec_generate.py patches Attention.__call__: when
#   cache.offset > 0 and s > 1, it unrolls into s lazy attn.step() calls in
#   one graph. This is numerically the EXACT op sequence sequential decode
#   performs per position (same window ring writes, same compressor steps,
#   same indexer top-k), so attention-side byte-identity holds by
#   construction. The MoE path stays batched over the s tokens
#   (StreamingExperts dispatches s>1 through gather_qmm/get_many), which is
#   where the 43 per-layer np.asarray syncs live -> syncs per pass collapse
#   from 43*s to 43. That is the entire point.
# - Window ring hazard checked: window_size=128. Batched writes of future
#   positions would clobber slots that earlier in-batch queries still need
#   once the ring wraps (slot (p+j)%128 == slot of p+j-128, which is inside
#   query p's window). The unrolled-lazy-steps approach dodges this entirely:
#   MLX arrays are functional, each step reads the array version as of its
#   position, so in-graph sequential ring writes are correct at any offset.
# - KV rewind on partial acceptance: per-position reference snapshots taken
#   after each in-graph step (offset, kv, idx_kv, comp.kv_state/score_state,
#   idx_comp state). Saving attr references IS the snapshot (setitem rebinds
#   — same trick as optimistic.py _snapshot/_restore). Restore to snaps[a]
#   = state after the last accepted input token. This also covers the
#   compressor partial-span state and its destructive shift(), which
#   position-overwrite semantics alone would NOT cover (spans closed by
#   rejected drafts shift() the rolling state).
# - Residual byte-identity risk (empirical, gated below): the verify pass
#   computes gate scores / expert FFN batched (gather_qmm over s tokens) vs
#   decode's per-token quantized_matmul loop; GEMM tiling differences could
#   in principle flip a near-tied argmax. The correctness gate tests this.
#
# Method: prompt-lookup (n-gram) drafting, greedy verification. Draft = copy
# of the continuation of the most recent longest n-gram match (n from n_max
# down to n_min=2) of the current suffix over prompt+generated ids. No draft
# model. Output provably identical to plain greedy modulo the fp caveat above.
#
# All timed runs: caffeinate -i, one model process at a time (pkill + verify
# dead first), separate cold process per configuration, --cache-gb 8.
#

DIAGNOSTICS (scratchpad diag_spec.py / diag2_exact.py, teacher-forced on the
sequential reference tokens, capitals prompt):
1. Batched verify (model.__call__ over s=9 with unrolled per-position
   attention): 0/48 argmax mismatches BUT logit top-2 margin drift up to
   ~1.0 from pos 13 on (e.g. 10.24 vs 9.40; 0.52 vs 0.14). Cause: MoE gate
   GEMM, gather_qmm (vs decode's per-expert quantized_matmul), and hc
   projections run different-shaped kernels at s>1 -> different fp
   accumulation. Near-tied positions (country names, margins ~0.15-0.5)
   can flip -> the gate-1 divergence. CONCLUSION: no multi-token-batch
   verifier that changes kernel shapes can be byte-identical on this stack.
2. Exact verify (_verify_exact: every op per token at decode shapes;
   batched ONLY per-layer index sync + get_many union prefetch):
   BITWISE identical teacher-forced, 0/24 positions differ. ~3.2 s per
   9-token chunk in-process.
3. Rewind was NOT bitwise (8/10 positions after rewind, max|d| up to 2.9),
   diverging exactly at the first ratio-4 span closure after the rewind
   point. ROOT CAUSE — PROJECT LORE OVERTURNED: mx.array.__setitem__
   mutates the SAME Python object in place (verified with a 6-line repro:
   b = a; a[0] = 1 -> b shows the update, a is b). "Saving attr references
   IS the snapshot because MLX setitem rebinds" (optimistic.py) is FALSE
   for setitem-updated buffers (LayerCache.kv/idx_kv, CompressorCache
   kv_state/score_state via write()/shift()). optimistic.py's restore never
   noticed because its repair-redo reruns the SAME token at the SAME
   position -> rewrites byte-identical values -> rollback was a no-op.
   FIX: snapshot = x[:] (new object wrapping the current value node; the
   later scatter replaces only the original object's node). Position-
   overwrite semantics alone would NOT have sufficed: the compressor
   rolling state is destructive (shift(), slot reuse across spans), and
   window-ring overwrite-safety breaks once the ring wraps (stale slot
   (p+j)%128 sits inside earlier queries' windows).

============================== ANALYSIS ==================================
VERDICT: the hypothesis FAILS on this stack in the regime that matters.
Speculative decoding reduced forwards per token by up to 35% (1.32-1.56
tokens/forward) with provably identical output — and LOWERED throughput in
every single configuration (0.44x-0.96x). The per-forward-pass cost is not
approximately fixed; it scales with the tokens in the pass.

Where the 43-sync amortization went:
1. A verify token costs about as much as a decode token, because both are
   dominated by expert traffic, and expert traffic scales with DRAFTED (not
   accepted) tokens. Each in-pass token routes to ~6 mostly-fresh experts
   per layer; the union get_many is mostly misses at an 8 GB budget. GB
   read tracks wall time across all 14 runs: A plain 206 GB -> k8 344 GB;
   C2 plain 274 GB -> k8 550 GB (for the SAME 96 emitted tokens).
2. In-pass marginal cost per token, measured (extra decode time / passes /
   s, attributing surrounding plain steps at the plain-run rate):
   A exact k4 ~0.82 s, A exact k8 ~0.68 s, C2 exact k4 ~1.49 s — equal to
   or HIGHER than the plain per-token cost (A 0.47 s, C2 1.38 s).
   Amortization is zero-to-negative before acceptance even enters, so no
   acceptance rate can rescue it: speedup ~= (a+1)/(k+1) <= 1.
3. Second-order pollution: rejected drafts' experts churn the LRU (~350+
   blob inserts/pass), evicting the warm set the interleaved plain steps
   rely on — the spec runs' plain steps are themselves slower.
4. Batched-mode kernels do not save it (A: batched k4 1.02 < exact k4
   1.12; batched k8 0.60 < exact k8 0.84): the gather_qmm stacking copies
   (~14.16 MB x union x 3 projections per layer per pass) plus the same
   IO dominate — and it loses byte-identity.
5. The store's per-blob Python cost (pread + np.frombuffer + 9 mx.array
   creations + LRU bookkeeping, ~1-3 ms/blob) multiplies with union size.

Why the hypothesis looked right: the "~128 ms compute + ~284 ms syncs"
accounting was measured in the 100%-hit WARM regime (2.43 tok/s ceiling),
where per-pass overhead really is the whole cost. In that regime spec
decode WOULD win (estimate: s=9 exact-mode pass ~ 9x128ms + 300ms = 1.45 s
vs 9 x 410 ms sequential = 2.7x at full acceptance). But the warm regime
exists only for degenerate prompts; realistic decode at 8 GB streams
2-3 GB/token and is IO-bound, and spec decode multiplies exactly the
IO term. Same shape as the project's cache-sweep lesson: the fixed-cost
model held only in the regime where it was measured.

WHAT A REAL DRAFT HEAD (DSpark MTP) WOULD NEED FOR 2x: on the current
store, no acceptance rate suffices — perfect acceptance only reaches
~(plain per-token)/(in-pass per-token) ~= 0.7-1.0x. 2x requires first
making in-pass tokens genuinely marginal, i.e. store/runtime work, in
order of leverage:
  a. batch the union's blob decode + insert (one np.frombuffer over the
     miss batch, vectorized mx.array creation) and overlap get_many preads
     with the previous layer's compute (drafts are known at pass start;
     hash layers 0-2 are prefetchable from token ids alone);
  b. batch the resident path (accepting fp-tolerant verification or a
     compiled runtime that makes batched==single bitwise);
  c. the compiled runtime that removes the 43 syncs AND the per-blob
     Python cost.
  With (a)+(b) landed and the warm-regime numbers as the floor (pass ~=
  0.43 s + s x ~0.05 s IO-effective), 2x over the 0.47 s/tok capitals
  baseline at k=8 needs (a+1) >= 2*(0.43+9*0.05)/0.47 ~= 3.7, i.e.
  ~34% token-level acceptance — well within MTP-head territory. On
  today's Python store, the answer is simply: not reachable.

SIDE FINDINGS (stand on their own):
* PROJECT LORE CORRECTED: mx.array.__setitem__ mutates the same Python
  object; reference-saving is NOT a snapshot (optimistic.py's trick).
  optimistic.py's rollback only ever worked because its redo rewrites
  identical values. Correct snapshot: x[:] (new node-wrapping object).
  Any future MLX rollback/rewind code must copy-by-node, not by-ref.
* A bitwise-exact multi-token decode-append verify EXISTS for this model
  (spec_generate._verify_exact): per-token ops at decode shapes, batched
  only in the per-layer index sync and get_many prefetch. Teacher-forced
  bitwise 0/24, post-rewind bitwise 0/10, 8/8 byte-identical end-to-end
  runs. Reusable for any future MTP/self-spec work.
* Any verifier that changes kernel shapes (batched MoE/hc) is NOT
  byte-identical on this stack: logit margin drift up to ~1.0, determin-
  istic argmax flips at near-tied positions (margins 0.14-0.52 observed).
  Greedy spec-decode "provable identity" assumes bitwise-equal forwards —
  false across MLX GEMM shapes.
* Prompt-lookup acceptance on real prompts: capitals 0.22-0.41 (structure
  accepted, novel content rejected), JSON schema 0.20-0.31, freeform 0.0,
  numbered-list-of-unique-items ~0 (looks structured, draws zero n-gram
  repeats). Draft-quality, not draft-length, is the binding constraint:
  raising k 4->8 never raised accepted tokens (23->23, 31->34) but always
  raised bytes read ~25%.
