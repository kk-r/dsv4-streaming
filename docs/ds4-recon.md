# Recon: antirez/ds4 ("DwarfStar") — SSD expert streaming in a compiled runtime

*2026-08-15. Read-only recon of [antirez/ds4](https://github.com/antirez/ds4) (21,380 stars, last push 2026-08-09, HEAD `84cc882` "rocm: enable DSpark speculative decoding") and the downstream fork [peppe200175/ds4_RTX_5080_cuda](https://github.com/peppe200175/ds4_RTX_5080_cuda) (HEAD `9be43d2`). Sources: shallow clones read locally, upstream issues via the GitHub API, and the fork's HN thread. File references are to the clone at commit `84cc882`; line numbers will drift.*

ds4 is a self-contained C/Objective-C inference engine ("DwarfStar") specialized for DeepSeek V4 Flash, V4 PRO, and GLM 5.2, with Metal, CUDA, and ROCm backends. It does not link GGML but adapts GGUF quant layouts and kernels from llama.cpp (README "Acknowledgements"). It is not a general GGUF runner: it only accepts its own published GGUFs (`README.md` "Model Weights"). Everything below is about the parts that overlap with this project: `--ssd-streaming`, the mode where non-routed weights stay resident and routed experts stream from the GGUF on demand — exactly our problem, in a compiled runtime.

---

## 1. Architecture: how ds4 executes streamed MoE

**Mode.** `--ssd-streaming` keeps non-routed weights resident and serves routed experts from "an in-memory cache … loaded from the GGUF file on cache misses" (README "Running models larger than RAM"). Help text (`ds4_help.c:170`) says it now covers "Metal/CUDA/ROCm", though the README body still describes it as Metal + ROCm-for-GLM; the CUDA path was substantially community-built (see §6).

**Unit of transfer: one expert's gate/up/down tensor slices, read straight from the GGUF — no repack step.** GGUF stores routed tensors expert-major, so each expert's slice of each tensor is contiguous; the pending-load structure carries per-selected-expert `gate_abs_offsets` / `up_abs_offsets` / `down_abs_offsets` and up to `3 * MAX_SELECTED` pread tasks (`ds4_metal.m:11838-11874`), i.e. **three preads per expert** versus our one 9-slice concatenated blob. There is no on-disk repacking; the 154 GB duplicate copy our `repack.py` creates has no equivalent — the model file itself is the store. (`ds4_layer_pack.c` is unrelated: multi-GPU layer placement.)

**I/O mechanism: explicit `pread` via a worker-thread pool, layered over an mmap'd model, with active page-cache management.**
- The whole GGUF is mmap'd into "no-copy" Metal buffer views (`ds4_metal.m:29` "mmap-backed weight views").
- Misses are loaded by a dedicated pread thread pool (`g_stream_expert_pread_pool_*`, `ds4_metal.m:~12060-12250`) into **mlock'd single-size-class slab buffers** wrapped as Metal buffers (mlock warnings at `ds4_metal.m:12296,12419`; slab allocator comment: "the cache is a single-size-class slab allocator … off-size layers are REJECTED", with mixed-precision "boosted" layers falling back to the mapped-model path).
- macOS readahead hints via `fcntl(F_RDADVISE)` (`ds4_metal.m:11804-11836`), optional `posix_madvise(WILLNEED)` (`ds4.c:17626-17677`, env-gated), and — the notable part — **`posix_madvise(DONTNEED)` on eviction** (`ds4_metal.m:12794-12820`), so evicted experts' file pages are surrendered back rather than left to compete. Per-cache counters exist for exactly this: `evict_dontneed`, `miss_willneed`, `miss_pread` GiB (`ds4_metal.m:3985`).
- On Linux/CUDA, staging reads use **`O_DIRECT`** when available, with alignment handling and graceful fallback to buffered `pread` (`ds4_cuda.cu:2099-2133`, fd setup at `4328-4344`).

**Caching policy: global (not per-layer) slab cache keyed `(layer, expert)`, victim selection by routing hotness, not LRU/LFU-on-hits.** Capacity table is `80 layers x 384 experts` max entries (`ds4_metal.m:608-612`). Two design comments are directly relevant to us:
- "The residency policy is global: every layer can use any expert slot it routes to … A per-layer cap made cache size depend on model depth rather than the actual byte budget" — independently the same conclusion as our lesson 10 (global LRU beats per-layer allocation, skewed working sets).
- "Route hotness counts selected experts even when they miss. Hit-count LFU penalizes experts that are repeatedly selected but evicted before a second hit" — victims are chosen by selection-frequency hotness with decay (`DS4_METAL_STREAM_EXPERT_HOTNESS_DECAY_TOKENS = 16`, `ds4_metal.m:611`), via a global victim scan per miss (with a note that batching victim scans helped GLM-size slots but regressed larger Q4 slots).

**Cache-overflow behavior is the structurally interesting bit: no thrash, spill to mmap.** When a layer's selected set exceeds what the cache can hold, the extra experts are *not* fetched into slots — "the extra experts are addressed straight into whole-tensor mapped model views instead of falling back to a different MoE kernel path. The address-table kernels read identical expert bytes either way." The GPU kernel consumes a per-expert address table that mixes cache-slab pointers and mmap-view pointers; overflow experts are served by page-cache/page-fault reads with no eviction pressure on the cache. This is a hybrid of our two poles (explicit LRU vs page cache): the cache holds the hot set, the page cache absorbs the tail.

**Startup: popularity-based hotlist preload.** The repo ships measured expert-popularity tables — `ds4_streaming_hotlist.inc` (13,334 lines; `ds4_default_streaming_hotlist_pro` and `..._flash` arrays of `{layer, expert}` sorted by hits/weight) plus a GLM variant — and by default pre-seeds the cache with up to 4,096 hot experts ("Auto mode is a hot seed, not a request to synchronously fill the whole cache", `ds4.c:20762-20780`). `--ssd-streaming-cold` disables it; a locality profiler (`ds4.c:~1236-1560`, "Metal Routed Expert Locality Profiler") records histograms and can write new hotlist files.

**Budgeting.** `--ssd-streaming-cache-experts NGB` is a routed-expert budget that first reserves headroom for "the two full routed layers used by overlapped streaming prefill", then converts the rest to expert slots; auto mode takes 80% of the backend's recommended working set minus non-routed weights (`ds4_ssd.c:80-135`, README). The 80% is documented as OOM-safety on unified-memory APUs, "measured safe" on ROCm (`ds4_ssd.c:95-105`). GLM's Metal path additionally keeps "the largest full-layer prefix that fits resident" and streams only the remainder (`--ssd-streaming-full-layers`).

## 2. The routing→fetch serialization (our 300 ms/token problem)

This is the thing our Python prototype cannot fix and ds4's whole decode design addresses. Mechanisms, all in the per-layer decode path (`ds4.c:~24300-24420`):

1. **Overlap expert fetch with the shared expert.** The decision flags are explicit: `overlap_selected_shared` / `async_selected_load` (`ds4.c:24330-24356`). After the router kernel produces selected ids, an **async service thread** stages the cache load (peek, slot assignment, pread-pool dispatch) *while the GPU computes the shared expert*, which depends only on `ffn_norm`, not on routing. A ROCm-path comment states it plainly: "Stage that compact selection while the shared expert runs so decode reaches the existing pointer-backed MoE path." The service thread is forbidden from waiting on in-flight GPU work; if it can't stage without waiting, the main thread retries synchronously ("The worker read valid ids but could not stage the load … This thread is [allowed to wait], so retry the same load synchronously"). A fallback mode `selected_readahead_shared_delay` just issues `F_RDADVISE` for the selected experts and lets the OS page them in during the shared-expert matmuls.
2. **Resident/missing split with I/O–GPU overlap.** Within one layer, cached ("resident") experts are submitted to the GPU immediately; the CPU preads the missing ones concurrently; a second "missing" stage then binds and completes: "The resident stage was submitted before the CPU read of missing experts so I/O can overlap with GPU work … the down/sum pass is issued once after all six mid slots exist; this keeps the final accumulation order stable regardless of the resident/missing split." Timing telemetry names every stage: `resident_submit`, `missing_load/slot/prune/addr/wait`, `load_pread`, `readahead` (`ds4_metal.m:3801`).
3. **Multi-layer command buffers.** Decode encodes batches of layers per Metal command buffer with tuned split points so CPU encoding of later layers overlaps GPU execution of earlier ones (comments around "routed decode exposes enough GPU work after layer two to overlap encoding before the layer-32 flush"; a streaming "layer batch" mode is default-on, `metal_graph_stream_decode_layer_batch_enabled`, `ds4.c:17571`). There is no per-layer host sync round-trip of the kind MLX's `mx.eval` forces on us; the only readback per layer is the tiny selected-ids tensor, and even that is hidden behind the shared-expert overlap.
4. **Prefill is a different regime entirely: layer-major with double-buffered whole-layer loads.** For long prompts, streaming prefill walks layer-major, preparing each layer's full routed expert set with parallel "pagein" worker threads (pread and/or madvise, `metal_graph_stream_pagein_job`, `ds4.c:17706-17805`) and readahead of the next layer — hence the reserved "two full routed layers" of budget headroom. Short streamed prefills instead use the decode-style path because it is latency-sensitive ("Short streamed prefill is latency-sensitive. Use the decode-style path by default for SSD streaming"). Prefill batch loads may *read* the expert cache and append into free capacity but **never evict** — "a long prompt cannot cycle out warm decode working set" (design carried into the CUDA cache work, issue #605) — which is precisely the prefill-evicts-decode failure mode we chased with `DSV4_PREFILL_NOCACHE`.
5. **Hash-routed layers** (`ffn_gate_tid2eid`) are handled by a CPU router path and are excluded from the async-selected machinery (`ds4.c:24325,24345`) — routing is known from token ids without any GPU readback, the same prefetch opportunity we identified and never exploited.

## 3. DSpark / MTP speculative decoding

Yes — first-class and current. DSpark is DeepSeek's auxiliary draft model for Flash 0731, packaged as a separate ~5.6 GiB support GGUF (`./download_model.sh ds4f-dspark`); it reads the main model's hidden states and proposes up to 5 tokens, which the target model verifies in one batched pass; a confidence threshold (default 0.6 Metal / 0.7 CUDA+ROCm) prunes low-yield suffixes (README "DSpark Speculative Decoding"). Accepted blocks keep the verifier's state rather than re-decoding, so long greedy runs can diverge in FP-reduction order from one-token decode (`--dspark-strict` restores byte-exactness). It replaces the older one-stage `--mtp` path, is greedy-only, opt-in, and disabled while native session batching is active. ROCm gained it in the HEAD commit (`84cc882`).

**Interaction with streaming:** explicitly supported — "On Metal, the main model may be resident or use `--ssd-streaming`; the support model still adds its own weights and runtime state to the memory requirement" (README). Verification of the ≤5-token block runs layer-major through the decode pair kernels ("MTP verification is neither normal decode nor large prefill … the decode pair kernels are exactly the right primitive", `ds4.c` comment), so speculative verification hits the same streaming expert cache/address-table path; per accepted block the expert working set per layer is up to 5×6 selections resolved in one pass instead of five separate fetch rounds — speculation amortizes the fetch serialization as well as the compute. No streaming-specific DSpark scheduling was found beyond that.

## 4. Platform support and the Apple Silicon story

- **Metal is the primary target** ("Metal, the primary target, on Macs with 96 GB or more. Smaller machines can use SSD streaming") — native Metal kernels in `metal/*.metal` + `ds4_metal.m` (43k lines), not MLX. M5-generation specific exact-fusion work is extensive (recent commits: "metal: push exact M5 q2 decode past 45 tok/s").
- CUDA: single-GPU, DGX Spark/GB10, multi-GPU tensor/expert parallel (8x L40S serving config in README). ROCm: Strix Halo (`STRIXHALO.md`).
- CPU path exists but is "reference/debug", not production.
- No MLX involvement upstream; issue #24 (closed) was an experimental community "mlx-flash-style streamed model access" branch that antirez took as the starting point for streaming ("adds streamed model weight access … splits streamed decode work so evictions can drain between layers. It is still slow, but it avoids full model residency"). Distributed modes (pipeline parallel over TCP, tensor parallel over Thunderbolt RDMA between two Macs) are Mac-centric.
- Adjacent ecosystem datapoint: [ssd-moe/deepseek-v4-flash-mlx](https://github.com/ssd-moe/deepseek-v4-flash-mlx) claims V4-Flash on a 48 GB Mac via MLX SSD expert-streaming at ~4.5–5 tok/s (2 stars, unverified, describes the model as "~100B MoE" — treat with caution, but it is a second MLX streaming implementation to diff against ours).

## 5. Quantization formats; repacking

- **GGUF only, and only their own files** from `huggingface.co/antirez/deepseek-v4-gguf`. Flash: `ds4f-q2` (routed experts up/gate `IQ2_XXS`, down `Q2_K`, everything else untouched — "very asymmetrical quantization"; ~81 GB), `ds4f-q2-q4` (last 6 expert layers q4), `ds4f-q4`, `ds4f-mxfp4` (native MXFP4 routed experts preserved from DeepSeek's release, ~156 GB; Blackwell uses native FP4 instructions). PRO q2-imatrix for 512 GB machines. imatrix versions preferred; local GGUF/imatrix tooling in `gguf-tools/`.
- **No expert repacking for locality** — none needed: GGUF's expert-major tensor layout already gives contiguous per-expert slices, and ds4 preads gate/up/down separately per expert directly from the model file. Our repack solves a real problem for *our* checkpoint format (9 scattered slices per expert) but also costs a full duplicate copy of the expert weights; ds4 spends zero extra disk.
- The closest thing to derived formats: optional CUDA "derived artifacts" repack for integrated GPUs (`ds4_gpu_build_derived_artifacts`, `ds4_cuda.cu:4350+`), and Q8/F16 device-side weight caches — device-format concerns, not disk-locality ones.

## 6. Performance claims (with hardware context)

Resident (non-streaming) reference points, README "Speed" (ds4-bench, q2, Promessi Sposi corpus): M5 Max 128 GB Metal **790 t/s prefill / 39.4 t/s decode** at 2K ctx (27.6 t/s at 64K); DGX Spark GB10 **826 t/s / 18.1 t/s**; M3 Ultra 512 GB PRO q2 at 32K ctx 138.8 / 9.6 t/s.

Streaming datapoints:

|---|---|---|---|---|
| Mac Studio M1 Ultra **64 GB** | Flash q2-imatrix (~81 GB), `--ssd-streaming-cache-experts 32GB`, 2K–32K ctx | ~108–118 t/s | **~5 t/s**, flat with ctx | issue #350 (closed, folded into speed-bench) |
| same, simulated 32 GB free | `--simulate-used-memory 32GB` | ~60 t/s | **~0.17 t/s** ("not practically usable") | issue #350 |

| DGX Spark GB10 | Flash, CUDA streaming + community LRU port, 100 GB budget | — | 1.03 → **2.96 t/s** (81% hit rate) | issue #639 |
| RTX PRO 6000 96 GB | Flash q4 from tmpfs, CUDA + restored resident expert cache | — | 2.3 → **29–32 t/s** warm | issue #605 (PR) |
| **RTX 5080 Laptop 16 GB VRAM** + NVMe, Linux/WSL2 | fork: CUDA streaming + 7 GB VRAM persistent expert cache, 132K ctx | — | **~3.7 t/s** | HN item 49273916 (author-confirmed) |

Notes on the 5080 fork: it adds only 3 commits over upstream — a metrics/web-chat restore, `cuda: add correctness-gated persistent expert cache` (`4476047`, +230 lines in `ds4_cuda.cu`: a VRAM-resident `(layer,expert)` cache filled only from the verified sequential SSD loader, hits served by device-to-device copies), and a 7 GB-budget/132K-ctx server default (`run_ds4_cuda_server.sh`). Its README is byte-identical to upstream; the 3.7 tok/s figure exists only in the HN thread ("Yes it's the best performance i can reach with a lot of caching between network layers of experts"). Context that makes the fork make sense: upstream CUDA's `--ssd-streaming-cache-experts` was **silently inert** — budget setters were no-op stubs and every token re-fetched every selected expert from the mapped file (issue #639, open; #647 and #605 are competing community LRU ports). The fork is one of at least three parallel fixes for the same gap.

Caveat for comparisons with us: all ds4 streaming numbers are q2-class quants (~7.4 MB/expert routed weights); our 2.04 tok/s is mixed 4/8-bit (14.16 MB/expert) — roughly 2x the bytes per miss.

## 7. Verdict

**What to steal (ranked by expected value to us):**

1. **Overlap expert staging with routing-independent compute.** ds4 hides fetch latency behind the shared expert (`overlap_selected_shared`/`async_selected_load`) and hides encoding behind execution with multi-layer command buffers. Our 284 ms/token is 43 per-layer `mx.eval` syncs; the transferable *shape* of the fix is: evaluate routing indices async, run the shared expert (and next layer's attention where legal) while the store stages misses, and split each layer into a dispatch-hits-now / join-misses-later pair. Even in Python/MLX a partial version (kick `store.get_many` on a worker as soon as indices are known, overlap with the shared-expert matmul) attacks the same bubble.
2. **Never-evict-on-prefill.** Their prefill can read and fill the expert cache but never evicts decode's warm set. This is a direct, cheap hypothesis for our open decode-after-long-prefill collapse — freeze LRU eviction during `get_many` prefill batches (insert only into free slots) and measure decode after. Our F_NOCACHE experiment protected the *page cache* from prefill; this protects the *LRU* from prefill, which we never tried.
3. **Hotlist preload + selection-hotness eviction.** Ships measured `{layer, expert}` popularity tables and seeds ≤4096 experts at startup; evicts by selection-count-with-decay because "hit-count LFU penalizes experts that are repeatedly selected but evicted before a second hit" — which is *exactly* the regime our diverse eval measured (each expert re-fetched ~7x, hit rate pinned ~53%). Our profiling data (9,344-expert union, per-layer skew) is one script away from being a hotlist.
4. **madvise discipline as the LRU/page-cache peace treaty.** `DONTNEED` on eviction, `F_RDADVISE` before need, mlock only the slab cache. Our lesson 6 said "make the two mutually exclusive rather than stacked"; ds4 shows the concrete mechanism. Also their overflow path — address the tail directly out of mmap instead of thrashing the cache — is a cleaner architecture than our all-through-LRU store.
5. **Hash-layer CPU routing** (tid2eid) is special-cased on their side too; we identified it and never built it.

**What we have that ds4 lacks (i.e., what our data is worth upstream):**

- **A measured cache-size↔throughput curve with replicates.** ds4's sizing guidance is anecdotal ("increase only while the machine remains responsive"); the auto 80% figure was "measured safe" only on ROCm, and their 64 GB Mac guidance (32 GB cache) has a single-issue datapoint behind it. Our 19-run both-directions sweep, the hit-rate/throughput anti-correlation, the swap-ratchet observation, and headroom-over-capacity methodology are directly contributable evidence — with the caveat that their DONTNEED/mlock design changes the economics, so the sweep must be *rerun under ds4*, not just cited.
- **Per-layer working-set skew numbers** (3x spread) — they reached the same global-policy conclusion but publish no numbers.
- **A 64 GB M5-generation Apple Silicon streaming benchmark.** speed-bench has M5 Max 128 GB resident and M1 Ultra 64 GB streaming; nobody has published the 64 GB M5 Pro streaming point, which is exactly our machine.
- **Quality niche:** all their streaming practice is q2; nobody has characterized streaming mixed 4/8-bit (better output distribution, 2x miss bytes) — our whole premise.

**What ds4 does worse than us:** honestly, at the runtime level, nothing relevant — it is our "compiled runtime" endgame already built, and its 64 GB Apple Silicon streaming decode (~5 t/s q2) beats our 2.04 t/s (mixed 4/8) with prefill ~50x ours. Its weaknesses are project-level: CUDA streaming cache landed broken and is being fixed by three uncoordinated forks; benchmark rigor behind the streaming advice is thin; the repo is huge (66k-line `ds4.c`), fast-moving, beta, and deliberately narrow to their own GGUFs — our checkpoint (pipenetwork mixed 4/8 MLX format) is not loadable by ds4 at all without a GGUF conversion.

**Contribute vs. Swift port: contribute.** The planned Swift/Metal port would re-derive, alone, what ds4 already has: pread pools, async staging, resident/missing split, slab cache, hotlists, DSpark. The quantified case for our port was the 284 ms of Python sync overhead; ds4 is the existence proof that the compiled runtime works and is ~an order of magnitude ahead of where a from-scratch port would land in any reasonable time. Higher-leverage plan: (a) run ds4f-q2 `--ssd-streaming` on our M5 Pro 64 GB with our benchmark discipline (caffeinate, replicates, both-directions cache sweep, swap tracking) and contribute the speed-bench CSV plus a cache-size sweep — it would be the first rigorous 64 GB M5 datapoint and directly tests whether our page-cache-over-LRU finding survives their DONTNEED design; (b) file our sweep methodology + per-layer skew data against their auto-budget planner (`ds4_ssd.c`) and issues #639/#647 where cache policy is actively being decided; (c) keep this Python/MLX repo as the measurement lab and the only runner of the higher-quality quant, not as the seed of a competing runtime. The one argument left for the Swift port is pedagogy — the stated goal of this project is learning — but if the port proceeds it should be read against ds4's decode path first, not designed blind.
